The documented `_refund` input supplies original transaction ID and amount but no immutable refund-request ID. Returning native success there would let WHMCS append another refund after the callback returns. The addon therefore owns persistent financial operation identity, SDK mutation, authenticated settlement and native bookkeeping; the legacy callback returns an actionable error.

`addInvoicePayment` takes an explicit positive decimal amount; zero/empty would mean the full balance and is forbidden. `AddTransaction` requires `paymentmethod`, not `gateway`, and returns `result` without a transaction ID. The adapter queries its unique reference and validates the written DECIMAL balances. Refund rows use the documented original-transaction relationship rather than guessing a native refund-column name.

Native invoice balance accessors are floats. The adapter reads exact DECIMAL native data, keeps monetary API values as canonical minor-unit strings with exact integer arithmetic, and rejects conflicting owner/currency or later invoice changes. The test-only schema/model in `tests/native-contract.php` is a stand-in, not a claim to redistribute or reproduce WHMCS internals. Actual schema/helper transactions must pass `licensed-acceptance.php`.

Lunixi financial/authentication/settlement rules come solely from bundled PHP SDK 1.0.1 Commerce. Create-intent returns `paymentId`+`token` and optional backend `paymentPageUrl`; authenticated GET identifies `data.id`; the actual merchant signed webhook envelope uses `id`, `type`, `environment`, `data.intentId`/`orderId`. Browser callbacks are not settlement evidence. A newer SDK can be built only after reviewing its contract and rerunning this module's tests.

Embedded checkout is the new-profile default. Hosted mode remains optional; the URL is validated and encrypted by the shared Commerce kernel, may carry an independent token, and is never assembled from the browser token. Missing/legacy URL does not rotate an attempt key or change its saved origin/body/mode.
